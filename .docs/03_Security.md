# 安全与权限（RBAC + 数据范围）

> 真相来源：系统角色、权限点、**数据维度与范围**、脱敏与审计基线。各功能规格（`/.docs/features/`**）中的权限矩阵（如 Template §9.1）描述**本功能操作与角色/权限点的关系**；**同一角色在不同人身上的数据范围**不在各功能里重复定义，而遵循本节「授权模型」。

---

## 2. 权限点清单（功能操作）

> **维护规则**：每个可鉴权的操作（菜单、按钮、API）对应一个**权限点编码** `perm_code`；新增能力时在本表登记，并在实现中与 `@PreAuthorize` / 网关 / 前端 v-permission 等对齐。


| 权限点编码 `perm_code`         | 说明   | 典型触发场景（可选） |
| ------------------------- | ---- | ---------- |
| （示例）`fdc:document:export` | 文档导出 | 批量导出、导出任务  |
|                           |      | 按模块持续追加    |


- **与角色关系**：见 §4「角色-权限模板」；角色是权限点的**打包**，不直接在业务代码里写死「只有某人」。

## 3. 数据维度（Data Scope）

> **含义**：控制「有权限点后，还能操作哪些数据」。同一 `role_code` 在不同人身上可绑定**不同的维度取值范围**（如不同归档主体、不同业务模块）。


| 维度编码 `scope_dimension` | 中文名称  | 说明            | 取值来源（与数据模型对齐）                 |
| ---------------------- | ----- | ------------- | ----------------------------- |
| `ARCHIVED_ENTITY`      | 归档主体  | 可管辖的法人/归档主体范围 | 主数据：`fdc_archived_entity_t` 等 |
| `BUSINESS_MODULE`      | 业务模块  | 可管辖的业务模块      | 主数据：`fdc_business_module_t` 等 |
| `E-FLOW_TYPE`          | 电子流类型 | 可查询的电子流类型     | Lookup：`E-FLOW_TYPE`          |
| `START_PERIOD`         | 档期    | 可查询的时间范围，年月格式 |                               |


- **维护规则**：新增维度类型时在本表增行，并在 `/.docs/01_DataModel.md` 中体现存储字段或关联表设计（避免文档与实现两套口径）。

## 4. 授权模型：角色模板 + 用户授权（含数据范围）

### 4.1 两层结构（必须区分）


| 层级                | 内容                                     | 维护位置                 | 说明                           |
| ----------------- | -------------------------------------- | -------------------- | ---------------------------- |
| **A. 角色模板（静态）**   | 某 `role_code` **默认拥有**哪些 `perm_code`   | 本文件 §4.2 + 配置表/初始化脚本 | 「文档管理员」这类人**能做哪些操作**         |
| **B. 用户授权实例（动态）** | 某用户被授予某 `role_code` 时，在哪些 **数据维度** 上生效 | 运行时表 + 申请审批流         | 同人不同岗：**同一角色、不同归档主体/业务模块范围** |


### 4.2 角色-权限模板（示例）

> 正式数据可用 `fdc_role_perm_t` 类表维护；此处为文档真相，表结构落地时与 `/.docs/01_DataModel.md` 对齐。


| `role_code`          | `perm_code`           | 备注           |
| -------------------- | --------------------- | ------------ |
| `FDC_ROLE_DOC_ADMIN` | `fdc:document:export` | 示例：文档管理员具备导出 |
|                      |                       | 继续罗列该角色其余权限点 |


### 4.3 用户授权 + 数据范围（申请与生效）

**一条用户授权记录**建议至少表达：

- **主体**：用户 ID（或工号映射用户 ID）
- **角色**：`role_code`
- **有效期**：可选 `start_date` / `end_date`
- **数据范围**：对 §3 中每个相关维度，存**允许 ID 列表**或**范围规则**（如：仅所选 `archived_entity_id` 集合 + 所选 `business_module_id` 集合）

**业务流程（建议）**：

1. **申请**：申请人选择 `role_code`，并勾选/填写本角色所需的**数据维度取值**（如多个归档主体、多个业务模块）。
2. **审批**：审批人按制度校验范围合理性；通过后写入「用户授权实例」表。
3. **鉴权**：接口除校验 `perm_code` 外，对资源行做 **scope 过滤**（文档的归档主体、业务模块必须在用户该角色绑定的范围内）。

**与功能规格的关系**：

- 功能规格 §9.1 矩阵：可写「某操作需要权限点 `xxx` + 数据范围按 §3 维度校验」。
- **不在**每个 feature 里维护「张三有哪些主体」；只在 **安全/运营功能**（角色申请、授权查询）规格中描述申请单字段与审批规则。

### 4.4 建议库表形态（落地时收入 01_DataModel）

> 以下为设计意图，物理表名与字段以实现为准，纳入 `01_DataModel.md` 后即为存储真相。

- **角色-权限**：`role_id` / `role_code` + `perm_code`（多对多）
- **用户-角色-范围**：用户 + `role_code` + 维度类型 + 维度取值 ID 列表（或子表一行一个 `dimension_value_id`）
- **审计**：授权变更（谁批、谁改、旧范围→新范围）单独记日志，满足合规
